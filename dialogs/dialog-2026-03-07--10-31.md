## 核心挑战：python-dotenv 是一个**库**，不是独立应用

这意味着"运行本项目"需要通过一个**演示脚本**来体现其价值，而不是直接启动某个服务。如何设计这个演示是关键。

---

## 方向一：演示脚本的设计思路

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **A：仅用 Python API** | 写一个 `demo.py`，用 `load_dotenv()` 和 `dotenv_values()` 读取 `.env`，用 `print` 输出结果 | 最直观，展示核心库能力 | 无法体现 CLI 功能 |
| **B：仅用 CLI 工具** | 全程用 `dotenv set / list / run` 命令操作 | 零代码，终端可见效果清晰 | 无法展示 API 灵活性 |
| **C：API + CLI 组合（推荐）** | 先演示 CLI 操作 `.env`，再演示 Python 脚本读取 | 全面，能展示两种典型使用场景 | 步骤略多 |

---

## 方向二：虚拟环境工具选择

| 方案 | 说明 | 推荐场景 |
|---|---|---|
| **`venv`（内置，推荐）** | Python 自带，无需额外安装，Windows 兼容性最佳 | 适合大多数开发者 |
| `virtualenv` | 第三方工具，功能更多 | 不必要，增加复杂性 |
| `conda` | 适合科学计算环境 | 该项目不需要 |

> 推荐使用 `venv`，步骤最简洁，在 Windows PowerShell 中开箱即用。

---

## 方向三：测试运行方式

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **直接运行 `pytest`（推荐）** | 在虚拟环境中安装依赖后直接运行 | 简单，无需额外工具 | 不含多版本矩阵 |
| `tox` | 多 Python 版本矩阵测试 | 完整 CI 体验 | 复杂，需要多个 Python | 
| `pytest` + 跳过 Windows 不兼容测试 | 直接运行但可能有少量测试因 `sh` 包失败 | 贴近真实情况 | 需解释哪些测试会失败 |

> **关键提示**：`sh` 包（Unix only）是测试依赖之一，Windows 上安装会失败，建议在文档中说明可用 `pip install pytest pytest-cov click ipython` 替代完整 requirements.txt 安装。

---

## 方向四：`.env` 示例文件的设计

为了让读者**看到实际效果**，示例文件应当包含：
- 普通键值对
- 包含注释的行
- 使用变量引用（`${VAR}`）
- 带空格/引号的值

这样可以在一个文件中展示 python-dotenv 最核心的几个特性。

4. **`.env` 示例**：包含变量引用、注释、多种值格式
