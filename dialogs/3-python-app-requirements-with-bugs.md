# 3 个调用 python-dotenv 的本地终端应用需求（含常见 Bug 分析）

> 用途：从中选择一个作为培训实战案例，让学员练习 AI 辅助软件开发工具的使用。
> 日期：2026-03-07

---

## 需求一：多环境配置切换工具（env-switch）

### 需求描述

一个本地终端工具，支持在 `development` / `staging` / `production` 等多个环境配置之间切换。工具读取 `.env.dev`、`.env.staging`、`.env.prod` 等文件，允许用户：

- 列出当前激活环境的所有配置键值
- 切换到指定环境（将目标文件的内容合并写入 `.env`）
- 显示当前端口号并自动计算调试端口（`APP_PORT + 1`）
- 支持用 `--key` 参数查询单个配置项的值

**核心 API 用法：** `dotenv_values()`、`load_dotenv()`、`set_key()`

### 学员容易引入的常见 Python Bug

| Bug 类型 | 典型错误写法 | 说明 |
|---|---|---|
| **类型错误 (TypeError)** | `port = os.getenv('APP_PORT') + 1` | `os.getenv` 返回 `str`，与 `int` 相加直接报错 |
| **KeyError** | `config['MISSING_KEY']` | 未用 `.get()` 导致 key 不存在时崩溃 |
| **布尔值陷阱** | `if os.getenv('DEBUG') == True` | 环境变量永远是字符串，`"true" != True` |
| **None 拼接** | `print("URL: " + config.get('BASE_URL'))` | key 不存在时 `.get()` 返回 `None`，字符串拼接报错 |
| **可变默认参数** | `def merge(base, extra={})` | 多次调用时 `extra` dict 被意外共享 |

### 特点

- **真实感强**：多环境切换是每个后端开发者都会遇到的日常场景
- **Bug 密度高**：类型转换、None 值、布尔判断三类 bug 可以自然地集中出现
- **范围可控**：核心逻辑不超过 80 行，适合 1~2 小时的实战练习

### 优势

- 需求直觉清晰，学员无需花时间理解业务背景
- 错误触发路径明确（切换环境 → 读端口 → 类型错误），便于 AI 工具辅助定位
- 可以自然地引导学员使用 `int(os.getenv('APP_PORT', '8000'))` 等防御性写法

### 劣势

- 文件操作依赖本地环境，不同操作系统路径行为略有差异，可能分散注意力
- Bug 相对集中在"类型转换"这一单一主题，覆盖的 Python 知识面稍窄

### 适用场景

- 适合 **Python 基础扎实但缺乏工程实践经验** 的学员
- 适合重点练习"AI 如何帮助定位 TypeError / KeyError"的课程模块

## 需求二：应用启动前环境变量校验工具（env-check）

### 需求描述

一个在应用正式启动前运行的"预检"脚本。它从 `.env` 文件加载配置，然后根据一份硬编码的"必需变量清单"（含类型约束和取值范围），对每个变量进行校验：

- 必填变量是否存在且非空
- 数值类型变量是否可转换为 `int` / `float`，且在合理范围内（如 `1 <= PORT <= 65535`）
- 布尔类型变量是否为合法值（`"true"` / `"false"` / `"1"` / `"0"`）
- 校验通过输出 `[OK]`，失败输出 `[FAIL]` 并汇总错误报告，退出码非零

**核心 API 用法：** `load_dotenv()`、`os.getenv()`、`dotenv_values()`

### 学员容易引入的常见 Python Bug

| Bug 类型 | 典型错误写法 | 说明 |
|---|---|---|
| **空字符串的假值陷阱** | `if not os.getenv('SECRET_KEY')` | `SECRET_KEY=` 时 getenv 返回 `""`，`not ""` 为 True，误判为"未设置" |
| **字符串布尔值误判** | `if os.getenv('DEBUG') == False` | `"false"` 永远不等于 `False`，条件永远不成立 |
| **裸 int() 转换** | `port = int(os.getenv('PORT'))` | 未加 `try/except`，非数字值直接抛 `ValueError` 使程序崩溃而非输出 FAIL |
| **用 `assert` 做校验** | `assert port > 0, "Port must be positive"` | `python -O` 运行时 assert 被跳过，校验失效 |
| **is 比较字符串** | `if os.getenv('ENV') is 'production'` | 小字符串驻留机制偶尔让 `is` 看似工作，实为未定义行为 |

### 特点

- **Bug 涵盖面广**：涉及假值判断、类型系统、异常处理、运行时行为四大类
- **输出结果可验证**：pass/fail 结果清晰，AI 工具的建议效果立竿见影
- **贴近真实工程**：CI/CD 流水线中的"前置检查"步骤在工业界极为常见

### 优势

- Bug 类型多样，适合讲解"Python 的字符串陷阱"专题
- 校验逻辑天然分层（必填 → 类型 → 范围），适合演示 AI 辅助重构
- 学员容易产生"我已经校验了"的错误自信，让 bug 更有教学价值

### 劣势

- 需求本身是"工具的工具"，略显抽象，部分学员可能需要额外引导
- 校验规则若设计过复杂，实现时间可能超出预期

### 适用场景

- 适合 **有一定 Python 经验、希望深入理解类型系统和异常处理** 的学员
- 适合重点练习"AI 如何解释 Python 的假值（falsy）语义"的课程模块
- 适合讲解"如何编写防御性代码"的进阶课程

## 需求三：团队 .env 文件同步与生成工具（env-sync）

### 需求描述

一个帮助团队维护 `.env` 文件一致性的本地工具。它以 `.env.example` 作为"模板"，对比实际的 `.env` 文件，并提供以下功能：

- **检查**：列出 `.env` 中缺少的 key（相对于 `.env.example`）和多余的 key
- **生成**：根据 `.env.example` 生成一份新的 `.env`，对于无默认值的 key 留空或提示用户输入
- **合并**：将两个 `.env` 文件合并，后者覆盖前者的同名 key（类似 `{**base, **override}`）
- **导出**：将当前 `.env` 的内容以 `export KEY=VALUE` 格式输出到终端，方便 shell 脚本使用

**核心 API 用法：** `dotenv_values()`、`set_key()`、`unset_key()`、`find_dotenv()`

### 学员容易引入的常见 Python Bug

| Bug 类型 | 典型错误写法 | 说明 |
|---|---|---|
| **迭代时修改字典** | `for k in config: config[k] = ...` | 边遍历边修改 dict 在 Python 3 中会抛 `RuntimeError` |
| **None 值写入文件** | `f.write(f"{k}={v}\n")` | `dotenv_values` 对无值的 key 返回 `None`，写入后变成字符串 `"None"` |
| **未用 with 打开文件** | `f = open('.env', 'w'); f.write(...)` | 异常时文件句柄泄漏，内容可能未刷新到磁盘 |
| **编码未指定** | `open('.env', 'r')` | Windows 默认 GBK 编码，读取 UTF-8 文件时中文注释乱码 |
| **`or` 默认值陷阱** | `value = config.get(k) or "default"` | `config.get(k)` 返回 `"0"` 或 `"false"` 时，因为是真值不会用 default；但返回 `""` 时会错误地用 default 覆盖有意设置的空值 |

### 特点

- **文件 I/O 与字典操作并重**：Bug 横跨两个维度，覆盖面最广
- **需求边界清晰**：diff / generate / merge / export 四个子命令，易于拆解成独立函数
- **错误后果直观**：`None` 被写进 `.env` 文件，学员打开文件就能看到问题

### 优势

- 是三个需求中 **工程复杂度最高** 的，适合训练学员使用 AI 工具进行整体设计和逐步实现
- 文件 I/O 的 bug（编码、句柄泄漏）在真实项目中极为常见，教学价值高
- `None` 值写入 `.env` 的 bug 需要学员真正理解 `dotenv_values` 的返回值语义，有深度

### 劣势

- 需求描述和子命令较多，初学者可能在理解需求上花费过多时间
- 涉及文件读写，测试时需要准备测试用的 `.env` 文件，环境搭建略复杂

### 适用场景

- 适合 **有一定工程经验、希望提升代码健壮性** 的中高级学员
- 适合以"完整功能开发 + 代码审查"为主题的全天实战工作坊
- 适合重点演示"AI 如何发现 None 值、编码和文件句柄等隐蔽 bug"的课程模块

## 选择建议

| 维度 | 需求一：env-switch | 需求二：env-check | 需求三：env-sync |
|---|---|---|---|
| 需求理解难度 | 低 | 中 | 中高 |
| Bug 覆盖广度 | 中（集中类型转换） | 高（多类 Python 陷阱） | 高（I/O + 数据处理） |
| 实现代码量 | 小（~80 行） | 中（~120 行） | 大（~200 行） |
| 适合课程时长 | 1~2 小时 | 2~3 小时 | 4~6 小时（全天） |
| AI 工具亮点 | 类型错误定位 | 语义陷阱解释 | 整体设计 + 隐蔽 bug |

**推荐入门课程选**：需求二（env-check）—— Bug 多样、需求清晰、输出可验证，是教学性价比最高的选择。

**推荐进阶课程选**：需求三（env-sync）—— 复杂度足够，能让学员深度体验 AI 辅助软件开发的全流程。
