# Bug 注入报告

## Bug 类型

**空字符串的假值陷阱（Empty String Falsy Trap）**

---

## 注入位置

- **文件**：`env-check/env_check.py`
- **行号**：第 42 行（`collect_errors` 函数内）

---

## 注入前的代码

```python
        if value is None:
            errors.append(f"[FAIL] {name}: 未设置")
            continue
```

## 注入后的代码

```python
        if not value:
            errors.append(f"[FAIL] {name}: 未设置")
            continue
```

---

## Bug 说明

`os.environ.get(name)` 在变量**未设置**时返回 `None`，在变量**设置为空字符串**（如 `DB_PASSWORD=`）时返回 `""`。

- `not None` → `True` ✅（正确：未设置）
- `not ""` → `True` ✅（误判：空字符串被当成"未设置"）
- `not "somevalue"` → `False` ✅（正常值不受影响）

`if not value:` 把 `None` 和 `""` 一视同仁，都走进"未设置"分支，导致空字符串的错误**被错误分类**，跳过了后续 `spec["type"] == "str"` 中专门针对空字符串的检查逻辑。

---

## 危害

| 场景 | 预期行为 | 实际行为（有 Bug） |
|---|---|---|
| `DB_PASSWORD=`（显式设为空） | `[FAIL] DB_PASSWORD: 值为空字符串` | `[FAIL] DB_PASSWORD: 未设置` |
| `DB_HOST=`（显式设为空） | `[FAIL] DB_HOST: 值为空字符串` | `[FAIL] DB_HOST: 未设置` |

错误信息类别错误，运维人员看到"未设置"会去检查变量是否存在于 `.env` 文件，而实际问题是变量存在但值为空。这会导致**排查方向错误**，延长故障定位时间。

更隐蔽的危害：如果未来有人在 `VALID_BOOLS` 逻辑里依赖"空字符串走 None 分支还是类型校验分支"的区别来做不同处理，整个类型分发逻辑都会静默出错。

## 如何修复

将 `if not value:` 恢复为严格的 `None` 判断：

```python
# 修复：只有真正的 None（变量未设置）才报"未设置"
# 空字符串 "" 应继续走后续类型校验逻辑
if value is None:
    errors.append(f"[FAIL] {name}: 未设置")
    continue
```

**根本原则**：在处理环境变量时，"变量不存在"（`None`）和"变量存在但值为空"（`""`）是两种不同的错误，必须分开处理，不能用 `not value` 合并判断。
